# Synthesizer V 가사 번역·보컬 정렬과 코드 구조 검토

프로젝트별 입력·보존 조건·결과물 이름은 [AGENTS.md](../../../AGENTS.md)를 따른다. 가사 및 타이밍 작업에는 아래 정렬 절차를, 관련 코드의 계획·수정·진단·리뷰에는 구조 검토 절차를 적용한다. 두 범위가 겹치면 두 절차를 함께 적용한다.

## 작업 유형 선택

- **음표 타이밍 조정**은 기존 가사를 기준으로 진행한다. 원본 가사 재배치도 요청받았으면 제공된 원문을 기준으로 아래 절차를 적용한다.
- **일본어→한국어 가사 번역 및 정렬**은 제공된 한국어 번역본이 있으면 이를 기준으로 삼는다. 번역을 요청받았으면 원문의 의미, 구절 순서와 반복을 한국어로 옮기고 실제로 부를 수 있는 음절 길이와 발음을 확인한다. 가창에 맞춰 의역이 필요한 부분은 근거를 기록한다. 한국어 가창본이 제공되면 그 발음을 타이밍 근거로 사용한다. 일본어 음원만 있으면 구절과 음표 위치의 참고 자료로 사용하고 한국어 발음의 실제 시작·종료는 확인 범위에 맞게 보고한다.

## 보컬 정렬

1. **기준 확보.** 해당 작업의 원본 SVP와 제공된 가사·타이밍 기준 자료를 확인한다. SVP의 트랙과 그룹 참조를 해석해 대상 라이브러리 그룹을 찾고, 음표 ID가 있으면 ID, 없으면 원본 그룹과 배열 인덱스로 대응표를 만든다. `onset`, `duration`, `pitch`, `detune`, `lyrics`와 원본 순서, 템포·박자, 그룹 오프셋, 트랙·음성·오디오 설정을 기록한다. WAV가 제공되면 실제 재생 길이와 SVP 타임라인에서의 기준 위치를 확인한다. TXT가 제공되면 실제 인코딩으로 읽고 원문을 보존한다.
2. **가사 대응.** 가사를 배치하는 작업에서는 확정 가사에 나온 순서대로 토큰과 음절을 대응시킨다. 단어의 철자·순서·반복을 기준 텍스트 위치로 역추적할 수 있게 남긴다. 실제 발음을 기준으로 음절 분할과 음절 하나가 여러 음에 걸리는 구간을 판단한다. 기존 음표와 음절 수가 어긋나면 해당 구간을 별도로 검토한다. 후렴은 반복마다 기준 가사와 사용 가능한 음원을 대조한다.
3. **발음 관측.** 대상 가창의 WAV가 제공되면 파형과 실제 발음을 함께 확인한다. 그 외에는 제공된 타이밍 기준과 확인할 수 없는 구간을 기록한다. 필요하면 스펙트로그램·청취·정렬 도구를 보조 근거로 사용한다. 단어·음절 시작, 자음과 모음의 시작이 다른 경우 그 차이, 지속 모음의 끝, 구절 사이의 공백을 기록한다. 자동 후보나 박자표만으로 확정하지 않는다. 첫 발음 전 구간부터 마지막 발음 이후까지 WAV 전체를 검토한다. 근거가 부족하면 시간 범위, 관련 음표·텍스트, 관측 근거와 공백을 `UNKNOWN`으로 기록하고 추측에 의한 수정은 보류한다.
4. **SVP 수정.** 확인된 타이밍 기준을 프로젝트 템포 맵과 해당 오디오·그룹의 오프셋을 사용해 SVP 단위로 변환한다. `onset`, `duration`과, 가사 배치가 작업 범위에 있을 때만 `lyrics`를 수정하여 별도 결과 파일을 만든다. 기존 상대 오디오 경로가 출력 위치에서도 해석되는지 확인하고 경로 문제가 있으면 기록한다. 여러 음표로 이어지는 음절은 사용하는 Synthesizer V 버전에서 동작을 확인한 표기만 적용한다. `UNKNOWN`은 검증 보고의 상태로 사용한다. 파일을 쓰고 다시 읽어 원본 대비 허용 필드 외 변경이 없는지 확인한다.
5. **전체 검증과 보고.** 원본·수정본을 음표 ID 또는 원본 인덱스로 대조하여 개수, 멜로디와 시작 순서, 음높이, detune, 그룹 참조, 기타 설정을 확인한다. `duration`은 양수여야 하며 새 중복·순서 역전·의도치 않은 겹침이 없어야 한다. 기존 가사를 유지하는 작업은 가사 필드가 그대로인지 확인한다. 가사를 배치한 작업은 음절 대응을 기준 텍스트의 토큰으로 복원해 반복을 포함한 전체 순서와 누락을 검사한다. 사용 가능한 타이밍 기준점에 대해 수정 전후 음표 시작과 측정 가능한 발음 종료·지속 시간을 비교한다. 허용 오차의 기준과 단위를 명시하여 큰 오차 구간을 보고하고, 원인이나 정렬이 미확정인 구간은 근거를 기록한다. 결과 파일의 파싱과 Studio Pro 실제 열기 결과를 따로 기록한다. 실행하지 못했으면 `NOT_RUN`과 이유를 남기고 최종 검증 상태를 `NOT_VERIFIED`로 표시한다.

## 책임 분리와 폴더 배치 검토

### 변경 전

1. 현재 요청 범위와 작업 시작 시점의 파일 상태를 기록한다. 자체 코드, 외부·벤더 코드, 생성 파일을 구분한다. 영향받는 단위의 전체 구현과 직접 연결된 호출자, 초기화·등록, 상태 쓰기, 콜백, 오류 처리 및 정리 코드를 읽는다. 진단이라면 증상이 드러난 지점, 관측 지점, 실제 판단 또는 결과 소비 주체를 구분한다.
2. 영향받는 단위별로 현재 책임과 근거를 적는다. 예를 들어 SVP 참조 해석과 포맷 직렬화는 같은 파일 형식 경계에 속할 수 있다. 음성에서 발음 시각을 추정하는 정책, 가사와 음표를 매칭하는 규칙, 검증 보고서의 출력 형식은 각자의 계약과 변경 이유를 살펴 판단한다. 하나의 진입점은 순서 제어와 기존 API를 유지하면서 독립된 구현을 해당 담당 모듈에 위임할 수 있다.
3. 분리가 필요하면 기존 또는 신규 담당자의 경로, 소유 상태와 쓰기 주체, 자원·초기화·정리 책임, 호출자와 호환성 제약을 기록한다. 새 폴더나 이동을 적용하기 전에 정확한 생성 경로와 이동의 출발·도착 경로, 변경할 참조, 배치 이유를 표시한다. 작업 범위와 직접 관련된 경계 단위로 진행한다.

### 구현과 배치

- 실제 코드가 필요할 때 SVP 입출력, WAV 분석, 가사 대응, 결과 검증 등으로 경계를 검토한다. `svp/`, `audio/`, `alignment/`, `verification/`은 역할이 실제로 존재할 때 선택할 수 있는 예다. 의존 방향을 정하고 기존 패키지와 모듈을 재사용한다. 파일 하나가 추가됐다는 이유만으로 하위 폴더를 만들지 않는다.
- 책임을 옮길 때 해당 정책, 상태, 설정, 자원, 초기화·리셋·종료 처리를 함께 옮긴다. 공개 또는 이전 호환 경로가 필요하면 명시적인 재노출이나 작은 어댑터를 유지한다. 구현 간 순환 참조가 생기면 실제 공유 계약만 독립 모듈에 두고 호출 방향을 바로잡는다. 새로운 공유 변경 가능 전역 상태로 경계를 연결하지 않는다.
- 공통 코드가 필요하면 기존 담당자, 집중된 함수, 위임 또는 합성을 먼저 비교한다. 상속은 현재 코드에 실제 `is-a` 관계와 안정된 공통 계약이 있고 모든 하위 타입이 그 계약을 지킬 때 사용한다. 상속 단계와 훅을 작게 유지하고, 검증·오류·정리 흐름과 기존 진입점의 호환성을 확인한다.
- 참조 변경은 import/export, 공개 API와 이전 경로, 설정 키와 경로, 등록·동적 로딩, 테스트·mock 경로, 빌드·패키징, 문서와 사용 예까지 실제 해당하는 범위를 확인한다. 진단 로그가 필요하면 실제 판단·전환과 결과를 제한된 범위로 관측하고 기존 오류·재시도·정리 흐름을 유지한다.

### 완료 확인

- 이동 후의 새 담당자와 원래 담당자 양쪽의 전체 상태·정책·수명·정리 및 실제 호출자를 확인한다. 이전 경로 검색과 순환 의존 확인, 일반 진입점을 통한 로딩, 필요한 구문·타입·집중 검증, 변경 사항 비교를 수행한다. 새 실패 동작을 바꾼 경우 그 동작과 결과를 확인할 수 있는 검증을 우선한다. 문서만 바뀌면 문서 내용, 경로, 링크 및 변경 범위를 확인한다.
- 구조 변경이나 요청된 구조 리뷰에는 다음 열을 사용해 의미 있는 책임 경계당 한 행으로 기록한다. 생성·이동 경로와 호환성 확인을 해당 행 또는 기존 변경 보고에 남긴다.

  | 변경 전 담당자와 소스 근거 | 책임과 배치 | 변경 후 담당자와 실제 경로 | 상태·쓰기·수명 이전 | 호출자·호환성·검증 | 남은 책임과 판정 |
  | --- | --- | --- | --- | --- | --- |

- 구조 상태는 `COMPLETE`(분리·배치·참조 확인), `NO_SPLIT_REQUIRED`(응집된 책임·기존 위임 또는 보존 예외), `INCOMPLETE`(필요한 분리·참조 갱신이 남음), `NOT_VERIFIED`(소스·호환성 등 확인 근거 부족), `OUT_OF_SCOPE`(구조 판정이 요청 범위 밖)로 기록한다. 구조 판정, 테스트, 파싱, 실제 앱 실행 결과는 각각 근거를 남긴다. 실행하지 않은 검사는 `NOT_RUN`과 이유를 적는다.
